# Игровой ассистент — контекст проекта

> **Новая машина или новый чат — начать с [docs/handoff.md](docs/handoff.md):** кто студент,
> сроки опроцентовок, договорённости, состояние работы, развёртывание с нуля. Этот файл
> описывает устройство проекта, тот — всё, что раньше жило только в переписке.

## Что это

Курсовая работа 7-го семестра, БГУИР, кафедра ИИТ, специальность «Искусственный интеллект».

**Тема: «Игровой ассистент».**

Кодовая база досталась с курсового проекта 6-го семестра (тема «интерфейс») — это игровой
ассистент для Minecraft: игрок пишет в игровой чат на естественном языке, LLM разбирает запрос,
сервер валидирует его и выполняет действие в игре (выдать предмет, призвать моба, завести
челлендж).

Руководство по курсовому проектированию в репозиторий не входит (репозиторий публичный);
на исходной машине оно лежало на уровень выше:
`../Руководство пользователя по курсовому проектированию (версия от 06.09.2026).pdf`.
Выжимка — в [docs/handoff.md](docs/handoff.md).

### Оформление записки — обязательно

Проверяющие придираются к оформлению; эти правила студент дал явно.

- Жирным не выделяется ничего, кроме названий разделов; курсив не используется. В перечне
  условных обозначений не выделяется ничего.
- Ссылка на источник — в конце абзаца, вплотную к последнему слову: `…слово\cite{X}.`
- Подпись таблицы — над таблицей, подпись рисунка — под рисунком.
- О прошлом семестре в записке не пишется ничего — только то, что есть и должно быть.
- Введение — не длиннее 1,5–2 страниц. Образец оформления — записка 6-го семестра,
  `report/reference/KP6sem.pdf`.
- Собранный `report/cource_report.pdf` хранится в репозитории: после правок исходников
  пересобрать `sh report/build.sh` и закоммитить вместе с ними.

### Что требует 7-й семестр (раздел 16 руководства)

плюс статистические/нейросетевые, объединённые в **одном сквозном процессе решения задачи**.
Ключевые запреты из руководства: нельзя «декоративный» нейрокомпонент, не влияющий на
результат, и нельзя изолированные компоненты без сквозного сценария.

Веса критериев оценки: архитектура и интеграция 25%, реализация обоих подходов 20%,
постановка задачи 15%, сквозные сценарии 15%, тестирование и самостоятельность 15%,

### Принятая политика поведения

**Никаких тихих исправлений.** Запрос понят не полностью — переспросить; запрос некорректен —
отказать с объяснением. Подставлять умолчание или молча чинить некорректный ввод нельзя.
Отсюда: «дай меч» → уточнение (захардкоженное умолчание `diamond_sword` подлежит удалению),
«дай 0 алмазов» → отказ, «дай 1000 алмазов» → выдать 64, **назвав** итоговое число.

**Запреты живут в базе знаний, а не в пробелах каталога.** Боссов и служебные блоки запрещает
явное правило, которое проверяет решатель и объясняет отказ. Подробности и таблица —
в [eval/README.md](eval/README.md).

### План работ семестра (дельта к существующему коду)

1. **База знаний.** Сделано: онтология игрового мира (RDF/OWL), 25 тыс. триплетов,
   1522 сущности, собирается импортёром из штатных JSON-данных Minecraft 1.20.1.
2. **Решатель.** Сделано: обратный вывод по графу способов получения с учётом инвентаря,
   валидатор с правом вето и объяснением отказа, проверка выполнимости задания.
3. **Нейрокомпонент и интеграция.** Сделано (этап 4): игровой чат `/api/rp/chat` проходит
   гибридный конвейер `orchestrator/` — модель извлекает намерение, резолвер по онтологии
   определяет объект, валидатор проверяет, планировщик строит план, модель формулирует ответ
   по выходу решателя. Режимы, задания с проверкой выполнимости, продолжения диалога,
   переформулировка неизвестных названий, вкладка «План» и переключатель режима в оверлее.
   Векторный слой резолвера проверен и отклонён по замеру
   (`eval/reports/2026-10-19-embedding-probe.md`).
4. **Эксперимент.** Три конфигурации прогоняются на золотом наборе с повторами
   (`--repeat`), сводная таблица с медианой и разбросом — `eval.compare`.
5. **Дальше — этап 5.** Довести золотой набор до ~100 реплик, прогон при ослаблении модели
   (пара gpt-oss 120B/20B заведена), протоколы тестирования, раздел 3 записки.

**Отложенный замер (на 2026-10-19).** Сводная A/B/C в `eval/reports/2026-10-19-comparison.md`
не окончательная: A прогнана один раз и ещё до исправления обрезки ответов (бюджет 200
токенов), C — трижды, но до исправления стоп-слов. Для честного сравнения нужно повторить
обе на одной модели — ~350 тыс. токенов, а суточный лимит Groq — 200 тыс. на модель
(скользящее окно). Выполнить в разные дни:

```bash
./.venv/Scripts/python.exe -m eval.runner --config llm_only --model gpt-oss-120b --repeat 3 --report
./.venv/Scripts/python.exe -m eval.runner --config hybrid   --model gpt-oss-120b --repeat 3 --report
./.venv/Scripts/python.exe -m eval.compare --save
```

Отчёты называются по дате и перезаписывают друг друга в пределах дня: прогон, оборванный
лимитом, затирает удачный — проверять поле «Сбоев связи» перед коммитом.

Версию Minecraft **1.20.1 не меняем** — мод под неё собран, данные версии пригодны для онтологии.

## Архитектура

Две части, общающиеся по HTTP:

```
Игрок → чат мода (Java/Fabric, MC 1.20.1)
  │  POST /api/rp/chat  {text}            инвентарь — из снимков, которые мод шлёт в /api/logs
  ▼
api/advice.py: команды режима и статуса заданий разбираются без модели, остальное —
orchestrator.Pipeline:
  ├─ extractor  — модель: реплика → {действие, название словами игрока, количество}
  ├─ resolver   — название → сущность онтологии (или уточнение, или «нет такого»)
  ├─ validator  — режим, существование, запреты, вид, количество; право вето
  ├─ planner    — план от инвентаря, развилки с отвергнутыми вариантами
  ├─ quest      — проверка выполнимости задания, одна попытка переделки
  └─ responder  — модель формулирует ответ только по выходу решателя; шаблон как запасной
  ▼
  ответ {response, execute, command, action_type, outcome, plan_tree, explanation, ...}
  ▼
мод выполняет команду; план — во вкладке «План» оверлея (клавиша O)
```

**Главный принцип:** модель называет объект словами игрока, а не идентификатором, и не видит
команду ни на одном шаге. Идентификатор подставляет резолвер, допустимость решает валидатор,
команду собирает сервер. Поэтому недопустимое действие нельзя получить формулировкой.

Режим (`creative`/`survival`) хранится в `orchestrator.session` и управляет составом действий,
предъявляемых модели; переключается фразой «режим выживания» или `POST /api/rp/mode`.

### Старый путь

`api/tool_service.py`, `api/minecraft_catalog.py`, `api/entity_catalog.py` и ключевые
слова в `api/advice.py` (`_looks_like_*`) — система прошлого семестра. В живом пути не
участвуют, но **не удалять**: на них построена конфигурация B, baseline сравнения.

### Модули

| Путь | Ответственность |
|---|---|
| `main.py` | FastAPI-приложение, подключение роутеров, отдача админки |
| `api/advice.py` | HTTP-слой: `/api/rp/` (пассивный поллинг), `/api/rp/chat` (диалог через `orchestrator`), `/api/rp/mode`, история, WebSocket |
| `api/groq_client.py` | Клиент LLM, мультипровайдерный: Groq, Ollama, OpenRouter, DeepSeek |
| `api/tool_service.py` | Реестр инструментов, серверная валидация и исполнение tool-вызовов |

| `api/entity_catalog.py` | То же для мобов |
| `api/minecraft_recipes.py` | Поиск рецептов по названию, валидация сетки 3×3 |
| `api/player_state.py` | Состояние игрока: убийства, инвентарь, экипировка |
| `api/challenges.py` | Челленджи; прогресс считается детерминированно из player_state, не из LLM |
| `api/wiki.py` | `/api/wiki/craft` — рецепт из базы, иначе fallback на LLM |
| `models/` | Pydantic-модели |
| `static/`, `frontend/js/` | Админка: 7 страниц (dashboard, settings, responses, player-state, challenges, analytics, wiki) |
| `mod/minecraft-mod/` | Fabric client-only мод, Java 17, MC 1.20.1 |
| `kb/` | База знаний: загрузка локали, извлечение данных игры, сборка онтологии, доступ через `kb.graph.KnowledgeBase` |
| `resolver/` | Сопоставление свободной речи с сущностями онтологии: нормализация и основы слов (`resolver.text`), индекс имён и оценка (`resolver.lexical`), политика ответа (`resolver.resolve`) |
| `orchestrator/` | Гибридный конвейер: `pipeline` (порядок компонентов, задания, продолжения), `extractor` (намерение моделью, промпт по режиму), `responder` (ответ по выходу решателя), `session` (режим, окно диалога, сводка фактами), `llm` (доступ к модели, повторы, обработка обрезки) |
| `api/compare.py` | Сравнение конфигураций на живой реплике для страницы `/compare` |
| `solver/` | Решатель: планировщик (`solver.planner`), валидатор действий и режимы (`solver.validator`), проверка заданий (`solver.quest`), вывод плана (`solver.render`) |
| `eval/` | Оценочный контур: золотой набор, раннер (`eval.runner`), конфигурации A/B/C (`eval/configs/`), сводная таблица (`eval.compare`), фиксация параметров модели (`eval.model_profile`) |
| `report/` | Пояснительная записка, LaTeX. Сборка — `sh report/build.sh` |
| `legacy/vision-assistant/` | Архив, к проекту не относится (см. ниже) |

## Команды

Окружение — `.venv` (старый `venv/` в репозитории собран на чужой машине и нерабочий).

```bash
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Запуск сервера (или `start_server.bat`):

```bash
./.venv/Scripts/python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Тесты (237 штук, все проходят):

```bash
./.venv/Scripts/python.exe -m pytest tests -q --ignore=tests/test_ui_smoke.py
```

Извлечение данных игры в `data/game/` (нужен собранный мод — jar берётся из кэша loom):

```bash
./.venv/Scripts/python.exe -m kb.fetch_locale   # русская локаль из ассетов Mojang
./.venv/Scripts/python.exe -m kb.extract        # рецепты, теги, дроп, инструменты
./.venv/Scripts/python.exe -m kb.build          # онтология в data/kb/game.ttl
```

Прогон золотого набора (см. [eval/README.md](eval/README.md)):

```bash
./.venv/Scripts/python.exe -m eval.runner --config symbolic --report
./.venv/Scripts/python.exe -m eval.runner --config llm_only --model gpt-oss-120b --report
./.venv/Scripts/python.exe -m eval.runner --config hybrid   --model gpt-oss-120b --report
./.venv/Scripts/python.exe -m eval.compare --save
```

Страница сравнения конфигураций для защиты — `http://127.0.0.1:8000/compare` при запущенном
сервере.

Мод (собирается за ~7 минут «на холодную», результат — `build/libs/ai-assistant-1.0.0.jar`):

```bash
cd mod/minecraft-mod && ./gradlew.bat build
```

Запуск dev-клиента Minecraft с модом (или `start_minecraft_client.bat`):

```bash
cd mod/minecraft-mod && ./gradlew.bat runClient
```

Файлы зависимостей:

- `requirements.txt` — ядро сервера, этого достаточно для запуска и тестов

## Подводные камни

- **`legacy/vision-assistant/` — чужая подсистема, к игровому ассистенту не относится**: захват
  экрана, vision, распознавание речи, TTS, оверлей на PyQt6. Писал одногруппник параллельно
  (ветка `cv-dev`), в пайплайн `/api/rp/` не входит, ничем из `api/` не импортируется. Раньше
  лежала в `backend/` и из-за названия читалась как серверная часть проекта. Chroma и
  sentence-transformers используются только там. Сохранена как задел под мультимодальность в
  дипломе, в курсовой не используется.
- **Эндпоинт называется `/api/rp/`, а модуль — `api/advice.py`.** Историческое расхождение,
  легко запутаться при поиске по коду.
- **Известные дефекты не чинить поштучно** — они зафиксированы в золотом наборе как точка
  отсчёта и переизмеряются после переработки. Список и цифры — в [eval/README.md](eval/README.md).
  Кратко: распознавание намерения по списку ключевых слов не ловит «нужен хлеб» и «хочу стейк»;
  нечёткое сопоставление подменяет предмет (`«5 алмазов»` → `diamond_block`) и срабатывает на
  несуществующем (`«призови дракона края»` → `enderman`); 8 зелий с NBT в идентификаторе не
  проходят `RESOURCE_ID_PATTERN` и невыдаваемы; в каталоге 50 дублирующихся id из 261 записи.
- **Один прогон с моделью — не измерение.** Даже при температуре 0 провайдер отвечает
  по-разному: два прогона с интервалом в минуты расходились на 1,5 пункта. Для цифр в
  записку — `eval.runner --repeat 3`, медиана и разброс.
- **Рассуждающие модели (gpt-oss) тратят бюджет токенов на рассуждение.** При 200 токенах
  JSON обрывался, и запрос молча становился «не действием». Бюджет в `orchestrator/llm.py`
  поднят до 600, обрезка (`finish_reason=length`) повторяется с удвоенным пределом, у gpt-oss
  в конфиге `reasoning_effort: low`.
- **Groq отвечает 403, если включён VPN.** Бесплатный OpenRouter — 50 запросов в сутки, на
  круг A/B/C не хватает. Модели провайдеры снимают без предупреждения: `qwen/qwen3-32b`
  пропал, заменён на `qwen/qwen3.8-27b`.
- **Тесты, создающие задания, обязаны подменять `challenges.CHALLENGE_STATE_PATH`** на
  временный файл: `create_challenge` пишет в `data/challenge_state.json`. До 2026-10-19
  тесты чата писали туда напрямую, и история заданий в рабочем файле засорена тестовыми
  записями.
- **Вкладка «План» в оверлее собрана, но вживую в клиенте не проверялась** — среды с окном
  игры у агента нет. Проверить при первом запуске `runClient`.
- **Системная `java` — это JRE 8, моду нужен 17.** Temurin JDK 17 установлен в
  `C:/Program Files/Eclipse Adoptium/jdk-17.0.20.101-hotspot`, и Gradle направлен на него через
  `org.gradle.java.home` в `~/.gradle/gradle.properties` — файл пользовательский, вне репозитория,
  на другой машине его нужно создать заново. `PATH` не трогали, поэтому `java -version` в консоли
  по-прежнему показывает 8; это нормально.
- **Ключи в `.env`** (`GROQ_API_KEY`, `OPENROUTER_API_KEY`, `DEEPSEEK_API`). Файл не
  отслеживается git — так и оставить, в коммиты не добавлять. DeepSeek (`deepseek-chat` в
  `llm_config.json`) — платный баланс около 10 $, запасной провайдер, когда квоты Groq не
  хватает; на полные прогоны золотого набора без нужды не тратить.
- Без ключа сервер поднимается и работает, но чат уходит в rule-based fallback
  (`source: "fallback"` вместо `"chat"`).
- **`data/challenge_state.json` — рантайм-состояние, снято с отслеживания** и внесено в
  `.gitignore`, иначе висело в каждом `git status`. При отсутствии файла `load_challenge_state()`
  подставляет состояние по умолчанию, так что на чистом клоне всё работает.
- **`.report/` (LaTeX-исходники пояснительной записки) в `.gitignore`** — то есть записка вне
  контроля версий. Для курсовой это стоит пересмотреть.
