# Игровой ассистент — контекст проекта

## Что это

Курсовая работа 7-го семестра, БГУИР, кафедра ИИТ, специальность «Искусственный интеллект».

**Тема: «Игровой ассистент».**

Кодовая база досталась с курсового проекта 6-го семестра (тема «интерфейс») — это игровой
ассистент для Minecraft: игрок пишет в игровой чат на естественном языке, LLM разбирает запрос,
сервер валидирует его и выполняет действие в игре (выдать предмет, призвать моба, завести
челлендж).

Руководство по курсовому проектированию лежит на уровень выше:
`../Руководство пользователя по курсовому проектированию (версия от 06.09.2026).pdf`

### Что требует 7-й семестр (раздел 16 руководства)

Гибридная интеллектуальная система: логико-символьные методы (база знаний, правила, вывод)
плюс статистические/нейросетевые, объединённые в **одном сквозном процессе решения задачи**.
Ключевые запреты из руководства: нельзя «декоративный» нейрокомпонент, не влияющий на
результат, и нельзя изолированные компоненты без сквозного сценария.

Веса критериев оценки: архитектура и интеграция 25%, реализация обоих подходов 20%,
постановка задачи 15%, сквозные сценарии 15%, тестирование и самостоятельность 15%,
оценка качества и эффективности 10%.

Ключевые документы:

- [docs/vision.md](docs/vision.md) — целевая система: что должно получиться к защите,
  сквозные сценарии, функциональность, критерии готовности;
- [PLAN.md](PLAN.md) — поэтапный план работ с привязкой к опроцентовкам;
- [docs/context-design.md](docs/context-design.md) — управление контекстом и памятью;
- [eval/README.md](eval/README.md) — оценочный контур, метрики, принятая политика поведения.

### Принятая политика поведения

**Никаких тихих исправлений.** Запрос понят не полностью — переспросить; запрос некорректен —
отказать с объяснением. Подставлять умолчание или молча чинить некорректный ввод нельзя.
Отсюда: «дай меч» → уточнение (захардкоженное умолчание `diamond_sword` подлежит удалению),
«дай 0 алмазов» → отказ, «дай 1000 алмазов» → выдать 64, **назвав** итоговое число.

**Запреты живут в базе знаний, а не в пробелах каталога.** Боссов и служебные блоки запрещает
явное правило, которое проверяет решатель и объясняет отказ. Подробности и таблица —
в [eval/README.md](eval/README.md).

### План работ семестра (дельта к существующему коду)

1. **База знаний.** Сейчас её нет в требуемом смысле — есть плоский справочник. Нужна онтология
   игрового мира (RDF/OWL) со связями между сущностями, собираемая импортёром из штатных
   JSON-данных Minecraft 1.20.1 (рецепты, теги, лут-таблицы).
2. **Решатель.** Сейчас его нет. Нужен обратный вывод по графу рецептов с учётом инвентаря
   (план достижения цели) плюс правила прогрессии/баланса/безопасности с правом **вето** над
   предложением LLM и объяснением отказа.
3. **Нейрокомпонент.** Заменить рукописный fuzzy-резолвер предметов на эмбеддинговый,
   существующий становится baseline для сравнения.
4. **Эксперимент.** Размеченный набор ~100 реплик игрока, три конфигурации: только LLM /
   только символьная (текущая система) / гибрид. Метрики: точность резолва, доля недопустимых
   действий, валидность плана, время отклика.

Версию Minecraft **1.20.1 не меняем** — мод под неё собран, данные версии пригодны для онтологии.

## Архитектура

Две части, общающиеся по HTTP:

```
Игрок → чат мода (Java/Fabric, MC 1.20.1)
  │  POST /api/rp/chat  {text}
  ▼
FastAPI-сервер (api/)
  ├─ groq_client.generate_tool_decision_async() → LLM выбирает tool + аргументы
  ├─ tool_service.execute_tool_call()           → серверная валидация и резолв ID
  ├─ groq_client.generate_tool_followup_async() → LLM формулирует ответ по результату tool
  ▼
  ответ {response, execute, command, action_type, ...}
  │
  ▼
мод выполняет команду в игре
```

**Важный архитектурный принцип, уже заложенный в коде:** LLM никогда не возвращает готовую
команду. Она выбирает только имя инструмента и передаёт запрос в свободной форме
(`item_query: "алмазы"`), а `/give`, `/summon`, `/clear` собирает сервер после детерминированного
резолва по каталогу. Это зародыш гибридной схемы — символьный слой как арбитр над
стохастическим генератором; в этом семестре он развивается от валидации параметров до
настоящего вывода по базе знаний.

### Инструменты (tool registry)

Определены в `api/tool_service.py::get_tool_registry()`:
`give_item`, `remove_item`, `summon_entity`, `create_challenge`, `claim_challenge_reward`.
Лимиты: не больше 64 предметов, не больше 16 мобов за раз.

### Модули

| Путь | Ответственность |
|---|---|
| `main.py` | FastAPI-приложение, подключение роутеров, отдача админки |
| `api/advice.py` | Основной оркестратор: `/api/rp/` (пассивный поллинг), `/api/rp/chat` (диалог), история, WebSocket |
| `api/groq_client.py` | Клиент LLM, мультипровайдерный: Groq, Ollama, OpenRouter |
| `api/tool_service.py` | Реестр инструментов, серверная валидация и исполнение tool-вызовов |

| `api/entity_catalog.py` | То же для мобов |
| `api/minecraft_recipes.py` | Поиск рецептов по названию, валидация сетки 3×3 |
| `api/player_state.py` | Состояние игрока: убийства, инвентарь, экипировка |
| `api/challenges.py` | Челленджи; прогресс считается детерминированно из player_state, не из LLM |

| `models/` | Pydantic-модели |
| `static/`, `frontend/js/` | Админка: 7 страниц (dashboard, settings, responses, player-state, challenges, analytics, wiki) |
| `mod/minecraft-mod/` | Fabric client-only мод, Java 17, MC 1.20.1 |
| `eval/` | Оценочный контур: золотой набор реплик, раннер метрик, отчёты |
| `legacy/vision-assistant/` | Архив, к проекту не относится (см. ниже) |

## Команды

Окружение — `.venv` (старый `venv/` в репозитории собран на чужой машине и нерабочий).

```bash
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Запуск сервера (или `start_server.bat`):

```bash
./.venv/Scripts/python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Тесты (94 штуки, все проходят):

```bash
./.venv/Scripts/python.exe -m pytest tests -q --ignore=tests/test_ui_smoke.py
```

Прогон золотого набора (см. [eval/README.md](eval/README.md)):

```bash
./.venv/Scripts/python.exe -m eval.runner --config symbolic --report
```

Мод (собирается за ~7 минут «на холодную», результат — `build/libs/ai-assistant-1.0.0.jar`):

```bash
cd mod/minecraft-mod && ./gradlew.bat build
```

Запуск dev-клиента Minecraft с модом (или `start_minecraft_client.bat`):

```bash
cd mod/minecraft-mod && ./gradlew.bat runClient
```

Файлы зависимостей:

- `requirements.txt` — ядро сервера, этого достаточно для запуска и тестов
- `requirements-dev.txt` — плюс pytest и selenium
- `requirements-vision.txt` — плюс архивная подсистема `legacy/vision-assistant/`, ставится долго (torch ~2.5 ГБ)
- `requirements.docker.txt` — минимальный набор для контейнера

## Подводные камни

- **`legacy/vision-assistant/` — чужая подсистема, к игровому ассистенту не относится**: захват
  экрана, vision, распознавание речи, TTS, оверлей на PyQt6. Писал одногруппник параллельно
  (ветка `cv-dev`), в пайплайн `/api/rp/` не входит, ничем из `api/` не импортируется. Раньше
  лежала в `backend/` и из-за названия читалась как серверная часть проекта. Chroma и
  sentence-transformers используются только там. Сохранена как задел под мультимодальность в
  дипломе, в курсовой не используется.
- **Эндпоинт называется `/api/rp/`, а модуль — `api/advice.py`.** Историческое расхождение,
  легко запутаться при поиске по коду.
- **Известные дефекты не чинить поштучно** — они зафиксированы в золотом наборе как точка
  отсчёта и переизмеряются после переработки. Список и цифры — в [eval/README.md](eval/README.md).
  Кратко: распознавание намерения по списку ключевых слов не ловит «нужен хлеб» и «хочу стейк»;
  нечёткое сопоставление подменяет предмет (`«5 алмазов»` → `diamond_block`) и срабатывает на
  несуществующем (`«призови дракона края»` → `enderman`); 8 зелий с NBT в идентификаторе не
  проходят `RESOURCE_ID_PATTERN` и невыдаваемы; в каталоге 50 дублирующихся id из 261 записи.
- **`temperature: 0.7` в `llm_config.json`** — сквозные тесты невоспроизводимы. Руководство
  требует фиксировать версии моделей и конфигурацию, так что для тестового контура нужен
  отдельный профиль с `temperature: 0` либо mock-LLM.
- **`max_tokens: 100`** во всех профилях — ответы обрезаются, для длинных объяснений плана
  придётся поднимать.
- **Системная `java` — это JRE 8, моду нужен 17.** Temurin JDK 17 установлен в
  `C:/Program Files/Eclipse Adoptium/jdk-17.0.20.101-hotspot`, и Gradle направлен на него через
  `org.gradle.java.home` в `~/.gradle/gradle.properties` — файл пользовательский, вне репозитория,
  на другой машине его нужно создать заново. `PATH` не трогали, поэтому `java -version` в консоли
  по-прежнему показывает 8; это нормально.
- **Ключи в `.env`** (`GROQ_API_KEY`, `OPENROUTER_API_KEY`). Файл не отслеживается git —
  так и оставить, в коммиты не добавлять.
- Без ключа сервер поднимается и работает, но чат уходит в rule-based fallback
  (`source: "fallback"` вместо `"chat"`).
- **`data/challenge_state.json` — рантайм-состояние, снято с отслеживания** и внесено в
  `.gitignore`, иначе висело в каждом `git status`. При отсутствии файла `load_challenge_state()`
  подставляет состояние по умолчанию, так что на чистом клоне всё работает.
- **`.report/` (LaTeX-исходники пояснительной записки) в `.gitignore`** — то есть записка вне
  контроля версий. Для курсовой это стоит пересмотреть.
