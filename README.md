# Minecraft AI Assistant (FastAPI + Fabric client mod)

Проект состоит из двух частей:

- **FastAPI сервер** (логи, настройки, выдача советов)
- **Fabric client-only мод** (сбор событий из игры, отправка логов на сервер, показ советов в игре)

## Структура

- `main.py` — FastAPI приложение
- `api/` — роуты (`/api/logs`, `/api/settings`, `/api/rp`)
- `models/` — Pydantic модели
- `static/` — HTML страницы админки
- `frontend/` — JS для админки
- `mod/minecraft-mod/` — исходники Fabric мода (Java 17, Minecraft 1.20.1)

## Быстрый старт (сервер)

### Способ 1: Через BAT файл (Windows, рекомендуется)

1) Двойной клик на `start_server.bat`
2) Сервер запустится на http://127.0.0.1:8000
3) Админка доступна по адресам выше

### Способ 2: Вручную через PowerShell

1) Создать и активировать виртуальное окружение:

```powershell
python -m venv .venv
.\.venv\Scripts\activate
```

2) Поставить зависимости:

```powershell
pip install -r requirements.txt   # ядро сервера
# pip install -r requirements-dev.txt      # + pytest, selenium
# pip install -r requirements-vision.txt   # + подсистема legacy/vision-assistant (vision, голос) — ставится долго
```

3) **Настроить Groq API (опционально)**

Для использования AI-powered советов:

a) Получить API ключ от [Groq Console](https://console.groq.com/keys)
b) Создать файл `.env` в корне проекта:

```env
GROQ_API_KEY=your_actual_groq_api_key_here
```

Если .env не создан или `GROQ_API_KEY` не установлен, система будет использовать правила-based советы (fallback).

4) Запустить сервер:

```powershell
python -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

5) Открыть админку:

- `http://127.0.0.1:8000/admin`
- `http://127.0.0.1:8000/admin/settings`

### Способ 3: Через Docker

Собрать образ:

```powershell
docker build -t minecraft-ai-assistant .
```

Запустить контейнер:

```powershell
docker run --rm -p 8000:8000 ^
  -v "${PWD}\data:/app/data" ^
  -v "${PWD}\settings.json:/app/settings.json" ^
  -v "${PWD}\llm_config.json:/app/llm_config.json" ^
  -v "${PWD}\llm_prompts.json:/app/llm_prompts.json" ^
  -e GROQ_API_KEY=your_actual_groq_api_key_here ^
  minecraft-ai-assistant
```

После запуска сервер будет доступен на `http://127.0.0.1:8000`.

Примечания:

- контейнер собирается только для текущего **FastAPI backend**, а не для Fabric-мода;
- данные каталогов и `challenge_state.json` сохраняются через `data:/app/data`;
- логи контейнера смотрятся через `docker logs`;
- если используется локальный Ollama с хоста, можно передать `-e OLLAMA_BASE_URL=http://host.docker.internal:11434/v1`.

## Каталог предметов и блоков для `/give`

Система выдачи предметов теперь использует локальный структурированный каталог `data/minecraft_catalog.json`, а не только свободный вывод LLM.

- `api/minecraft_catalog.py` загружает каталог и ищет совпадения по русским и английским названиям, aliases и токенам
- `api/advice.py` использует этот catalog lookup для deterministic resolution `minecraft:item_id`
- LLM теперь возвращает controlled tool-like payload (`tool_name`, `arguments`, `spoken_response`, `should_execute`), а не готовую команду
- backend выполняет только разрешённый `give_item`, сам валидирует `item_query` через каталог и только затем собирает безопасный `/give`
- благодаря этому обрабатываются и более свободные фразы вроде `мне бы 10 наковален` или `я бы не отказался от пузырька`
- локальный resolver теперь дополнительно чистит шумные слова из запроса, нормализует разговорные формы и использует fuzzy ranking, поэтому фразы вроде `бутылёк` тоже могут корректно матчиться
- reasoning/внутренние рассуждения модели в Minecraft chat не выводятся: игрок видит только финальную реплику
- при неоднозначном запросе вроде `дай доски` сервер просит уточнить предмет вместо случайного выбора

## Каталог существ для `/summon`

Система теперь умеет не только выдавать предметы, но и **призывать базовых существ** через отдельный tool `summon_entity`.

- `data/entity_catalog.json` хранит локальный каталог существ с русскими и английскими alias-ами
- `api/entity_catalog.py` детерминированно резолвит запрос игрока в `minecraft:entity_id`
- backend не доверяет модели готовую команду: LLM выбирает только tool и передаёт `entity_query`, а `/summon` собирается уже на сервере
- первая версия intentionally ограничена **базовыми мобами без NBT и без координат**
- `summon_entity` теперь умеет призывать **несколько мобов за раз** с безопасным лимитом до **16**, а mod-side выполняет такой summon как пакет отдельных `/summon`
- также появился tool **`remove_item`**, который детерминированно удаляет предметы из инвентаря через `/clear` и даёт базу под будущие обмены `забрать X -> выдать Y`
- если запрос явный, backend умеет собрать summon action даже через direct fallback, например для фраз вроде `призови зомби`
- continuation тоже поддерживается: после успешного призыва фразы вроде `и ещё крипера` могут идти через тот же tool loop

## Оптимизация LLM-вызовов

- routine `GET /api/rp/` больше не должен запускать LLM на каждый poll: для обычного пассивного RP используются cached/rule-based ответы
- LLM на стороне backend теперь в основном остаётся для player chat, tool invocation и отдельных critical events
- chat flow сведен к одному structured LLM вызову вместо схемы `action call + отдельный chat fallback`

Это сделано для того, чтобы блоки и предметы выдавались стабильнее, а knowledge layer можно было позже расширить до справочника команд.

## Prompts и chat memory

- prompt templates теперь лежат отдельно в `llm_prompts.json`, а `llm_config.json` хранит только выбор модели, provider и параметры
- interactive `/api/rp/chat` использует отдельную память диалога на последние **10 сообщений** (`user` / `assistant` / `tool` / `tool_result`), чтобы бот лучше помнил предыдущие реплики и результаты tools
- structured chat prompt теперь учитывает историю разговора и умеет выбирать между `give_item`, `remove_item`, `summon_entity`, `create_challenge`, `claim_challenge_reward` и обычным chat-ответом

## Player state telemetry: киллы и инвентарь

Поверх обычных логов backend теперь держит отдельный **shared player-state**, который нужен и для debug, и как foundation для будущих челленджей.

- Fabric-мод отправляет новые события:
  - `mob_kill` — факт убийства моба игроком
  - `inventory_snapshot` — агрегированное состояние инвентаря
- kill telemetry теперь идёт через **server-side Fabric event** `ServerLivingEntityEvents.AFTER_DEATH`, поэтому в `mob_kill` попадают именно реальные смерти от игрока, а не любые смерти рядом
- backend обновляет этот state в `api/player_state.py`, не полагаясь только на сырую историю `logs_db`
- в state хранятся:
  - `kill_counts`
  - `recent_kills`
  - `inventory.counts`
  - `hotbar`
  - `armor`
  - `offhand`
- для отладки появилась отдельная страница **`/admin/player-state`**
- LLM prompt context теперь может видеть compact summary текущих киллов и инвентаря, а не только последние логи

Первая версия inventory telemetry хранит:

- агрегированные counts по предметам;
- отдельно hotbar;
- отдельно armor;
- отдельно offhand.

## Челленджи поверх player-state

Поверх telemetry теперь появился отдельный **challenge-state** в backend:

- хранится один активный челлендж + история завершённых/отменённых;
- state сохраняется в `data/challenge_state.json`;
- progress считается детерминированно из `player_state`, а не из LLM:
  - `kill` → по `kill_counts`
  - `collect` → по `inventory.counts`
- создание первой версии идёт **через диалог с ботом** с помощью tool `create_challenge`;
- получение награды идёт через tool `claim_challenge_reward`, который использует уже существующий `give_item` flow;
- для debug появилась страница **`/admin/challenges`**.

Первая версия intentionally ограничена:

- только **один активный челлендж** одновременно;
- только цели `kill entity` и `collect item`;
- только reward типа `give_item`;
- награда выдаётся отдельным `claim`, а не автоматически в момент completion.

## Groq LLM Integration

Система советов теперь использует **Groq LLM** для генерации контекстных советов игроку на основе последних 5 событий из игры.

### Как это работает

1. Когда клиент запрашивает `GET /api/rp/`, система собирает последние 5 логов из игры
2. Эти логи отправляются в Groq API вместе с специально подготовленным промптом
3. LLM анализирует ситуацию (здоровье, враги, голод, время суток) и генерирует короткий совет
4. Совет отправляется обратно клиенту с источником `"groq"`

### Fallback механизм

Если Groq API недоступен или ключ не установлен, система автоматически переходит на **rule-based советы** (как было раньше):
- Проверяется здоровье, голод, враги, ночь
- Соответствующий совет выбирается по приоритету
- Совет отправляется с источником `"fallback"`

### Настройка API ключа

Требуется:
- Аккаунт на [groq.com](https://groq.com/)
- API ключ из [Groq Console](https://console.groq.com/keys)

После получения ключа:
1. Создайте файл `.env` в корне проекта (рядом с `main.py`)
2. Добавьте: `GROQ_API_KEY=your_key_here`
3. Перезагрузите сервер

Проверить, что работает:
```bash
curl http://127.0.0.1:8000/api/rp/
```

В ответе должно быть `"source": "groq"` вместо `"source": "fallback"`.

## Оптимизация советов (Rate Limiting & Change Detection)

Система советов теперь включает механизмы предотвращения спама:

### Rate Limiting (минимум 3 секунды между советами)

Даже если игровое состояние часто проверяется, советы не будут отправляться чаще, чем раз в 3 секунды. Это предотвращает спам в чате.

### Change Detection (отправка только при изменении ситуации)

Советы отправляются только если:
- **Уровень критичности изменился** (INFO → WARNING → CRITICAL)
- **Тип совета изменился** (например, с низкого здоровья на враги)
- Прошло достаточно времени с последнего совета

### Text Formatting (для длинных советов)

Длинные советы автоматически форматируются для удобства:
- Советы длиной >100 символов разбиваются на несколько строк
- Разбиение происходит по предложениям
- Текст остается полностью читаемым

### Результат

- ✓ Меньше спама в чате (максимум 1 совет в 3 секунды)
- ✓ Советы не "вылетают" за пределы экрана
- ✓ Советы отправляются только при реальных изменениях
- ✓ Первый совет отправляется сразу (без ожидания)

## Обработка смерти игрока (Death Event)

### Статус реализации

**Сервер:** ✅ Полностью готов (может обрабатывать события смерти)
**Мод:** 🔄 Требует реализации (готовы инструкции и код)

### Как это работает (полный цикл)

1. **Игрок умирает** → Здоровье: 20 → 0
2. **Мод обнаруживает смерть** (новое: checkForDeath метод)
3. **Мод отправляет POST** на сервер:
```json
{
  "event_type": "death",
  "event_data": {"cause": "fall"},
  "level": "ERROR",
  "message": "death: cause=fall",
  "player_health": 0.0
}
```

4. **Сервер получает** и добавляет в логи
5. **Запрос `GET /api/rp/`** обнаруживает смерть
6. **Возвращает CRITICAL** совет с confidence=1.0:
```json
{
  "advice": "Вы умерли! Причина: fall. Помните, где вы были, и подготовьтесь перед возвращением.",
  "confidence": 1.0,
  "level": "CRITICAL",
  "source": "fallback"
}
```

7. **Мод показывает** совет в игре (action bar)

### Добавить死смерти в мод

Смотрите документацию для разработчиков мода:
- **Быстрый старт:** `QUICK_DEATH_LOGGING_IMPL.md` (3 шага)
- **Пошаговое руководство:** `MOD_EDITING_INSTRUCTIONS.md` (4 редактирования)
- **Полная документация:** `MOD_DEATH_LOGGING_GUIDE.md` (все варианты)
- **Справочник:** `DEATH_LOGGING_QUICK_REF.md` (шпаргалка)
- **Готовый код:** `MOD_AssistantRuntime_UPDATED.java` (copy-paste)

### Возможные причины смерти

Мод автоматически определяет причину из `getLastDamageSource().getMsgId()`:

| Причина | Описание |
|---------|---------|
| `fall` | Падение с высоты |
| `mob_attack` | Атака мобом |
| `player_attack` | PvP урон |
| `drowning` | Утопление |
| `fire` | Огонь |
| `lava` | Лава |
| `cactus` | Кактус |
| `suffocation` | Удушение в блоке |
| `falling_block` | Падающий блок (песок, гравий) |
| `lightning` | Удар молнии |
| `void` | Падение в void |
| `generic` | Неизвестная причина |

## Дополнительные "Умные Фичи" (Новые Функции)

Недавно в систему были интегрированы две крупные фишки, превращающие ИИ-суфлера в мощного виртуального спутника:

### 1. Тактическая аналитика после матча (Post-Match Analytics)
**Цель:** Оценка качества игры пользователя, выявление критических ошибок (слишком частое попадание в лаву, потери здоровья от голода) и генерация тактических советов на будущие игровые сессии.

**Как это работает (Подробный разбор кода):**
- **Python (Backend):** В `api/analytics.py` создан новый роутер `GET /session_summary`. Этот эндпоинт агрегирует весь массив логов из памяти сервера (`logs_db`). Чтобы не "взорвать" лимит контекстного окна LLM (Context Window), мы на стороне Python делаем пре-агрегацию: считаем суммарное количество смертей и критических падений здоровья. Для LLM собирается короткий `timeline` (до 30 важнейших событий). 
- **LLM Промптинг (`api/groq_client.py`):** Агрегированные данные отправляются в метод `generate_analytics`. Метод использует специальный промпт киберспортивного аналитика. Важно: для этого мы временно поднимаем лимит `max_tokens` (с 100 для коротких советов до 800+), чтобы ИИ смог развернуто написать большой отчет в формате Markdown.
- **JavaScript (Frontend):** На новой странице `static/analytics.html` пользователь нажимает кнопку, которая триггерит AJAX запрос скриптом `frontend/js/analytics.js`. По возвращению JSON-ответа, счетчики (например, количество логов и смертей) вставляются в красивый HUD, а большой текстовый ответ ИИ парсится через библиотеку `marked.js`, сохраняя жирный текст, абзацы и списки.

### 2. AI-Справочник крафтов (Smart Wiki)
**Цель:** Заменить долгие переходы в Google или Minecraft Wiki на мгновенный, прощающий опечатки ИИ-поисковик прямо в админке. Нейросеть выступает как огромная база данных каждого рецепта в игре.

**Как это работает (Подробный разбор кода):**
- **LLM Промптинг (`api/groq_client.py`):** Самое интересное здесь — метод `search_crafting_recipe()`. Мы отключаем фантазию нейросети, ставя параметр `temperature = 0.0` (полностью детерминированный ответ). Мы строго заставляем ИИ выдать ТОЛЬКО валидный JSON (без "Конечно, вот ваш крафт!" и Markdown оберток) заданной структуры, описывающей массив 3x3 (сетку верстака). Пустые слоты обязательно заполняются словом `"пусто"`. Отдельно на Python очищается любой мусорный текст (например, блок ```json), спасающий от ошибки парсинга `json.loads()`.
- **Python (Backend):** В `api/wiki.py` мы прокидываем эндпоинт `GET /craft?query={item}` для обработки поисковой строки.
- **JavaScript (Frontend):** Скрипт `frontend/js/wiki.js` запрашивает бэкенд каждый раз, когда вы нажимаете Enter в строке поиска `static/wiki.html`. При получении матрицы крафта `3x3`, скрипт проходится двойным циклом `for(let row of recipe.grid)` и динамически встраивает новые `<div>` (ячейки) в элемент контейнера (DOM). Те ячейки, где текст отличен от `"пусто"`, закрашиваются плотным фоном (аналог слотов в верстаке), а остальные остаются прозрачными. Это на 100% повторяет эстетику оригинальной игры.
