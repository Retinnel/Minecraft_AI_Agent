# Оценочный контур

Размеченный набор реплик игрока и раннер метрик. Нужен для двух вещей:

1. зафиксировать, как работает текущая система, **до** того как она начнёт меняться;
2. поставить сравнение трёх конфигураций, которое требуется на высший балл: чисто
   символьная / чисто нейросетевая / гибридная.

Набор создаётся первым по порядку именно поэтому: если размечать после переделки резолвера,
разметка невольно подгонится под новое решение и сравнение потеряет смысл.

## Запуск

```bash
.venv/Scripts/python.exe -m eval.runner --config symbolic --report
.venv/Scripts/python.exe -m eval.runner --config hybrid   --model gpt-oss-120b --repeat 3 --report
.venv/Scripts/python.exe -m eval.runner --config llm_only --model gpt-oss-120b --repeat 3 --report
.venv/Scripts/python.exe -m eval.compare --save
```

С флагом `--report` результат складывается в `eval/reports/` двумя файлами: markdown для записки
и json для последующей обработки. `eval.compare` собирает сводную таблицу из последних отчётов
каждой конфигурации и предупреждает, если они сделаны на наборах разного объёма.

`--model` фиксирует модель на время прогона, не меняя файл настроек; температура при этом
ставится в 0.

`--repeat N` прогоняет набор N раз. **Для конфигураций с языковой моделью один прогон
измерением не является**: даже при нулевой температуре провайдер отвечает на один вход
по-разному, и два прогона с интервалом в минуты расходились на полтора пункта. В сводку идут
медиана и разброс, а реплики, исход которых менялся, перечисляются отдельно.

Сбой связи с моделью (недоступность, исчерпание квоты, обрезанный ответ) помечается исходом
`error` и в статистику решений не входит: иначе прогон мерил бы качество сети, а не системы.

## Конфигурации

| Ключ | Что это | Статус |
|---|---|---|
| `symbolic` | B — текущая система без LLM: ключевые слова, нечёткое сопоставление по каталогу, regex на количество | готова |
| `llm_only` | A — только языковая модель: сама называет идентификаторы, проверок нет | готова |
| `hybrid` | C — гибрид: тот же конвейер `orchestrator/`, что работает в игровом чате | готова |

Отдельные замеры:

- `eval.coverage` — покрытие и скорость планировщика по всей предметной области;
- `eval.embedding_probe` — годятся ли векторные представления для сопоставления названий
  (не годятся: отчёт `reports/2026-10-19-embedding-probe.md`).

Новая конфигурация — это модуль в `eval/configs/` с функцией `predict(utterance) -> Prediction`
и переменной `CONFIG`.

## Формат разметки

`golden_set.jsonl`, одна строка — один пример. Поля описаны в `schema.py`.

```json
{"id": "give-t-001", "utterance": "дай алмаз", "group": "typical",
 "outcome": "act", "intent": "give_item", "item_id": "minecraft:diamond", "count": 1}
```

`outcome` — чем должна закончиться обработка:

- `act` — выполнить действие;
- `clarify` — переспросить, запрос неоднозначен;
- `reject` — отказать: предмета нет либо действие недопустимо;
- `none` — это не запрос действия, обычная реплика.

`group` — `typical`, `boundary` (неоднозначность, предельные количества, словоформы) или
`negative` (несуществующее, запрещённое, противоречивое). Деление на эти три группы требуется
руководством.

`policy: true` помечает примеры, где правильный ответ зависит от решения о поведении системы,
а не от объективного факта, и это решение ещё не принято. Сейчас таких строк нет — принятая
политика описана ниже. Флаг остаётся для будущих спорных случаев.

## Метрики

Главных две.

**Доля совпадений с разметкой** — сколько примеров обработано ровно так, как размечено.

**Доля небезопасных расхождений** — сколько раз система уверенно и молча сделала не то. Это
важнее общей точности: отказ игрок видит и может переформулировать, а молчаливая подмена
предмета выглядит как нормальная работа. Сюда входят исходы `wrong_target`, `wrong_count`,
`wrong_intent`, `missed_clarify`, `spurious_act`.

Полный список исходов с пояснениями — в докстринге `classify()` в `runner.py`. Исход
`planned_instead` (построен план там, где ждали действие) к небезопасным не относится:
`plan_goal` не собирает команду и мир не меняет. То же для `answered_instead`: вместо
ожидаемого действия или болтовни система ответила на вопрос — из онтологии (`ask_uses`,
`ask_sources`, `ask_drops`, `ask_available`, `show_progress`) или из сети (`search_web`).
Такие действия только читают и команды не собирают (`READ_ONLY_INTENTS` в `runner.py`).

Отчёт прогона с моделью показывает и расход: входные и выходные токены на реплику и
долю входа, взятую из кэша провайдера (`orchestrator.llm.usage_report()`). Прогон гибрида
2026-11-23 (`reports/2026-11-23-hybrid-tokens.md`): 1159 входных и 48 выходных токенов на
реплику, из кэша 77,5 % входа — по тарифу DeepSeek около цента за весь набор.

## Веб-поиск

Золотой набор поиск не проверяет: ответ из сети меняется со временем, а прогон стоит
кредитов. Для поиска отдельный замер на десяти живых вопросах — шесть о Minecraft (тактика,
постройки, механики, выдуманное существо, плюс рецепт и добыча, которые обязаны уйти в
онтологию) и четыре о других играх, включая просьбу выдать предмет, которую там выполнить
нельзя:

```bash
./.venv/Scripts/python.exe -m eval.search_probe --report
```

Проверяется маршрут, а текст ответа сохраняется в отчёт для чтения глазами. Прогон
2026-11-23 на `deepseek-chat` и Tavily — `reports/2026-11-23-search-probe.md`: 10 из 10
маршрутов, семь ответов из сети, поиск 1,3–4,4 с, весь ответ 5–7 с. На выдуманный вопрос
(«как приручить розового единорога в аду») ассистент ответил, что в найденном этого нет.
Поиск DeepSeek как второй движок замерен 2026-11-24 на тех же десяти вопросах в один
день с Tavily (`reports/2026-11-24-search-probe-deepseek.md` и
`reports/2026-11-24-search-probe.md`; `--engine` задаёт движок, без него — цепочка как на
сервере). Оценки обоих движков приведены к общей шкале (`search.engines.normalize`), порог
0,3 один.

| Движок | Маршруты | Ответов из сети | Оценки страниц по теме | Поиск |
|---|---|---|---|---|
| Tavily | 10 из 10 | 7 | 0,74–0,86 | 0,9–1,8 с |
| DeepSeek | 10 из 10 | 6 | 0,45–0,79 | 1,2–1,4 с |

На трудном вопросе (диалог с Кровавым бароном) оба дают 0,4–0,7. Вопрос о выдуманном
существе: DeepSeek отбросил все пять страниц, Tavily принял две страницы модов с оценкой
0,31, и ответ честно сказал, что во фрагментах этого нет. Источники Tavily — вики
(minecraft.fandom.com, minecraft.wiki) и профильные издания, DeepSeek после исключения
сайта-агрегатора — polygon.com, gamerant.com, rockpapershotgun.com, thegamer.com.
Tavily остаётся первым.

После добавления действия `ask_about` («что это») набор перемерен 2026-11-24
(`reports/2026-11-24-hybrid.md`): 56 из 61, ноль недопустимых, исход реплик совпал в трёх
прогонах, новое действие не перехватило ни одной реплики; 1272 входных токена на реплику,
80,5 % из кэша.

Золотой набор после добавления поиска перемерен (`reports/2026-11-23-hybrid-search.md`,
`--tag search`): 56 из 61 во всех трёх прогонах, те же пять непройденных реплик, что и
2026-11-17, ноль недопустимых; в поиск не ушла ни одна реплика набора — действие не
перехватывает выдачу, планы и вопросы к онтологии. Что видно глазами и в цифры не попадает: один и тот же вопрос модель переводит по-разному
— «крепость края» в одном прогоне стала End City, в другом stronghold; ответ на вопрос о
диалоге в «Ведьмаке 3» пересказывает последствия выбора, а не реплику.

## Результат первого прогона

Конфигурация `symbolic`, 56 примеров: **совпало 53.6%**, небезопасных расхождений **10.7%**,
медиана отклика 22 мс.

Расхождения группируются в пять причин.

**Распознавание намерения по списку ключевых слов — 11 промахов.** `ACTION_REQUEST_PATTERNS`
содержит «дай», «выдай», «призови» и ещё несколько форм. Всё, что сформулировано иначе —
«нужен хлеб», «хочу стейк», «закинь тотем», «мне бы дебрис» — не распознаётся как запрос вообще.
Это структурное ограничение подхода: список слов не может покрыть естественную речь.

**Нечёткое сопоставление подменяет предмет — задеты 4 примера.** «дай мне 5 алмазов»
резолвится в `minecraft:diamond_block`, потому что токен «алмазов» совпадает с алиасом
«блок алмазов» и перевешивает правильный вариант. Та же подмена срабатывает в кейсах
`give-b-006`, `give-b-007`, `give-b-008`.

**Оно же срабатывает на несуществующем — 1 промах, самый показательный.** «призови дракона края»
превращается в `minecraft:enderman`: слово «края» совпало с алиасом «странника края». Система
молча призывает не того моба вместо отказа.

**Некорректное количество выполняется — 2 промаха.** «дай 0 алмазов» и «дай -5 алмазов»
приводят к выдаче: ноль нормализуется в единицу, а минус просто не виден регулярному
выражению `(?<!\w)(\d{1,3})(?!\w)`, поэтому «-5» читается как «5».

**Словоформы — 2 промаха.** «дай печку» и «призови слайма» отказывают: в каталоге есть «печь» и
«печка», но не «печку», есть «слайм», но не «слайма». Захардкоженный стемминг по префиксам
покрывает только те слова, для которых его писали руками.

Отдельно, не связано с резолвом:

**Путаница отказа и уточнения — 5 случаев.** На «дай мне звёздный меч» система переспрашивает,
зацепившись за «меч», вместо того чтобы сказать, что такого предмета нет.

## Дефекты, найденные при разметке

**Зелья невозможно выдать.** В каталоге 8 идентификаторов с NBT вида
`minecraft:potion{Potion:"minecraft:healing"}`. `RESOURCE_ID_PATTERN` в `api/tool_service.py`
допускает только `^[a-z0-9_.-]+:[a-z0-9_./-]+$`, то есть фигурные скобки, кавычки и заглавные
буквы отсекаются. Резолв проходит успешно, а валидация идентификатора затем отклоняет предмет,
причём с сообщением «Не смог понять, какой предмет нужно выдать» — то есть ошибка ещё и
диагностируется неверно. Кейсы `give-b-012`, `give-b-013`.

**В каталоге 50 дублирующихся идентификаторов** из 261 записи (уникальных 211). Похоже, два
источника слиты в один файл: сначала рукописные записи, затем алфавитный импорт. У дублей
разные наборы алиасов — например, у `minecraft:diamond` в одной записи «алмаз, алмазы, алмаза»,
в другой «алмаз, алмазик». Это напрямую влияет на ранжирование кандидатов при сопоставлении.

Чинить сейчас не нужно: эти цифры — обоснование переработки в аналитическом разделе записки.
После появления онтологии и эмбеддингового резолвера те же кейсы прогоняются повторно, и разница
идёт в третий раздел.

## Принятая политика поведения

Все спорные случаи разрешены; разметка ниже отражает согласованные решения.

**Никаких тихих исправлений.** Если запрос понят не полностью, система переспрашивает; если
некорректен — отказывает с объяснением. Молча подставлять умолчание или чинить некорректный
ввод нельзя: игрок не видит подмены и считает, что система его поняла.

Из этого следует:

| Ситуация | Решение | Пример |
|---|---|---|
| Запрос допускает несколько предметов | уточнение | «дай меч» → переспросить, какой именно |
| Запрос без предмета | уточнение | «дай» → переспросить |
| Предмета или существа не существует | отказ | «дай звёздный меч» |
| Количество некорректно (ноль, отрицательное) | отказ с объяснением | «дай 0 алмазов» |
| Количество превышает предел | выполнить с обрезанием, **назвав** итоговое число | «дай 1000 алмазов» → «выдаю 64» |
| Разговорная форма названия | выполнить | «бутылёк», «гэпл», «реда» |

Захардкоженное умолчание `«меч» → minecraft:diamond_sword` в `api/minecraft_catalog.py`
подлежит удалению: оно прямо противоречит принятой политике.

**Запреты живут в базе знаний, а не в пробелах каталога.** Призыв боссов и выдача служебных
блоков сейчас «запрещены» только тем, что этих записей нет в справочнике — то есть случайно.
На этапе 2 в онтологию вводится класс ограничений, а на этапе 3 решатель проверяет его явным
правилом и объясняет отказ. Кейсы `summon-n-001` (дракон Края) и `give-n-003` (командный блок)
проверяют именно это.

Показательно, что сейчас отсутствие записи не защищает: «призови дракона края» не отклоняется,
а нечётко сопоставляется с `minecraft:enderman` по слову «края» и выполняется.

## Куда расти

К этапу 5 набор нужно довести примерно до 100 примеров. Чего сейчас нет совсем:

- запросы на планирование («что нужно, чтобы сделать алмазную кирку») — появятся вместе с
  решателем;
- запросы с опорой на состояние игрока («хватает ли мне железа на броню»);
- многошаговые диалоги с уточнением;
- противоречивые запросы («дай алмазы, но не давай ничего»).

## Что в общий набор не входит

Вопросы о мире (`ask_uses`, `ask_sources`, `ask_drops`, `ask_available`, добавлены
2026-11-17) в набор не внесены по той же причине, что кампания и ступень: у конфигураций A
и B таких действий нет, и сравнение на них было бы сравнением наличия функции, а не
качества. Их добавление проверено иначе — гибрид перемерен на прежнем наборе, чтобы
убедиться, что четыре новых действия в подсказке модели не перетянули на себя старые
реплики: 56 из 61, ноль недопустимых, как и до того (`reports/2026-11-17-hybrid.md`).


Решено 2026-11-11. Реплики кампании («веди меня к…», «дай цель»), вопрос о ступени развития
и разбор гибели в общий набор **не добавляются**.

Причина — сопоставимость. Общий набор существует ради сравнения трёх конфигураций на одних
и тех же репликах, а у конфигураций A и B этих действий нет вовсе: каждая такая реплика
стала бы для них промахом по определению. Сравнение начало бы мерить не качество понимания
и не цену ошибки, а наличие функции — и разрыв в пользу гибрида вырос бы без всякой заслуги
архитектуры. Кроме того, отчёты до этой даты сняты на 61 реплике; расширение набора новыми
намерениями сделало бы их несопоставимыми с новыми.

Эти функции проверяются там, где проверка содержательна: сценарными тестами с моделью-
заглушкой (`tests/test_campaign*.py`, `tests/test_postmortem*.py`, `tests/test_progression.py`)
— в них сверяется вывод решателя, а не распознавание намерения. Если понадобится измерить
именно понимание таких реплик моделью, это отдельный набор только для гибрида, без строки
в сводной таблице A/B/C.

Расширение общего набора до ~100 реплик идёт по списку из раздела «Куда расти»: все четыре
вида запросов доступны каждой из трёх конфигураций хотя бы в принципе.

## Память мира: отдельный набор

Реплики о памяти («где я видел алмазы», «запомни, тут база», «забудь отметку») в общий набор
не входят по той же причине, что кампания: у конфигураций A и B таких действий нет. Они
размечены в `golden_memory.jsonl` — 10 реплик, формат общий, вместо предмета-цели метка
факта (`subject`). Ответ зависит от того, что игрок видел, поэтому прогон идёт с
зафиксированной памятью мира и позицией игрока из `memory_fixture.py`; каждая реплика
получает свежую копию памяти.

```
python -m eval.runner --config hybrid --golden-set eval/golden_memory.jsonl --memory --report --tag memory
python -m eval.plan_memory --report
```

Тест `tests/test_golden_memory.py` прогоняет набор через конвейер с заглушкой вместо модели:
проверяется всё, что после модели (валидатор, память, исход), — 10 из 10. Точность самой
модели на наборе ещё не измерена: прогон требует ключей провайдера.

Замер длины планов (`reports/2026-11-25-plan-memory.md`) от модели не зависит: 12 целей из
пустого инвентаря, с памятью короче все 12, действий всего 112 → 19, медиана сокращения
трудоёмкости 57.6%. Запасы сундука в фикстуре выбраны как типичные для середины игры, так
что это оценка сверху для игрока с припасами, а не среднее по реальным мирам.

## «Сделай сам»: отдельный набор

Намерение `execute_plan` предъявляется модели только при включённом автопилоте (раздел
`autopilot` в `settings.json`, по умолчанию выключен), поэтому общий набор его не видит и
его результат от фичи не зависит. Реплики «сделай сам …» размечены в `golden_autopilot.jsonl`
— 10 реплик, половина граничных: «сделай сам каменную кирку» против «как сделать каменную
кирку», а также отказы валидатора (глубокие руды, Незер, охота). Прогон идёт в выживании,
в одиночной игре, с Baritone и пустым инвентарём (`autopilot_fixture.py`).

```
python -m eval.runner --config hybrid --golden-set eval/golden_autopilot.jsonl --autopilot --repeat 3 --report --tag autopilot
```

Тест `tests/test_golden_autopilot.py` прогоняет набор с заглушкой вместо модели, которая на
двух граничных репликах нарочно путает `plan_goal` и `execute_plan`: конвейер поправляет её
по явным словам игрока («сам», «за меня» против «как», «что нужно»), — 10 из 10. Точность
модели на наборе ещё не измерена: прогон требует ключей провайдера с положительным балансом.
